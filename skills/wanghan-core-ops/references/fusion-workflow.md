# 核心运营与直播复盘融合协议

协议版本：2026-10-03。新分支核心运营思路为统一主入口；王焓直播复盘为兼容入口。两个入口执行相同证据链，交付同一份报告。复盘方法来源于王焓直播复盘0.4.0，融合时保留更严格的身份、ASR、场次及指标审查。

## 统一调用

用户调用任一入口，依次完成：目标与模块初判 → B站/Chrome证据采集 → 转写和说话人审查 → 时间轴校准 → 关键节点与五层漏斗 → 八模块战略判断 → 下一轮实验 → 一份统一报告。无需用户先调用另一个技能或重复提交资料。工具能力须实查，说明文件不能替代实际转写服务。

只做单场复盘时，保留该场范围；只给方案时输出实验设计；只要求切片时判断素材价值。不要为了融合而自动扩展到八个模块的全量策划。默认不写主播逐字稿或具体话术，用户明确要求时才下钻。用户已指定“提高进房与新人留存”且未改目标时，优先①/②与④承接，第⑧贯穿。

## 单一证据链与去重

为每个任务记录session_id、BV、分P、CID、媒体覆盖、转写版本/参数、数据窗口与状态。原始资料、转写结果、节点表和指标窗口共用；两个技能同时被@时，只建立一个任务，不各自启动ASR或输出两份报告。

优先复用同BV/分P/CID与参数相符且经质量审查的结果。completed只表示处理状态，不证明身份、ASR正确或全场覆盖。云端artifact可用而提交冲突时先复用artifact，不因提交冲突重复转写。后台新数据只补充现有场次；账号/场次不一致时禁止合并。

## 分阶段执行与状态

| 阶段 | 统一方法 | 通过条件 |
|---|---|---|
| 资料采集 | source-acquisition.md；B站链接与已登录Chrome机构版/抖音后台 | 实际读取返回资料，核对账号、场次和分P/CID |
| 内容审查 | live-review-method.md | 说话/音乐/噪声分区；身份和ASR质量分别核验 |
| 对齐与指标 | core-data-analysis.md、live-review-schema.md、measurement.md | 至少两个独立锚点，口径/单位/来源/人群可比；不确定区间保留 |
| 战略与实验 | 八模块与operations-department.md | 模块/功能 → 变量 → 核心指标 → 验证 → 结论标准 → 下一步 |
| 统一交付 | core-data-analysis.md | 一份报告、最多三项下一场动作及对应验证指标 |

状态分别写已完成、待补数、运行中、失败、未核验。证据采集完成、时间校准完成、效果验证完成是三种状态，不能互相替代。

## 冲突时采用的可信规则

- 主cluster、出现最早或说话最长只能提示候选，不能确认王焓；旧medium/high标签不自动进入王焓语料。无同录像已确认干净参考或等效人工核验，身份为未知/待核验。
- 王焓原话必须同时通过身份核验和独立ASR质量审查；唱歌/BGM/嘉宾不进本人口播语料。原文、自动识别、摘要与设计方案分开。
- 声纹不默认长期保存。若用户接受单参考核验，记录其明确授权、限制及保守模式，不能当成身份已校准。
- 曝光人数与曝光次数、进房人数与进房次数分开；不把分钟人数除以曝光次数当进房率。非粉丝不等于首次进房新人，离开/在线曲线不等于新人60秒留存；缺项留空。
- 至少两个共同锚点检验偏移；录屏0秒不自动等于开播。分P、剪辑、暂停使用分段偏移；未校准时只做各来源独立观察。
- 保留投流、PK、嘉宾、时段等混杂。单场峰值只说明同步变化，效果采用需要可比对照与重复验证。

## 输出与保存

先写有限度结论、所属模块和进房/留人/关系/消费/扩散功能，再给证据可信度、关键节点、五层漏斗、变量、指标口径、验证方式、结论标准及下一轮。回答什么拉人、什么留人、什么产生互动/消费、哪里浪费流量；无数据的回答标待验证。

八模块与默认执行顺序保持：①画面形象+②流量切入 → ③女性向中医/④长期内容 → ⑤消费人群/⑦粉丝粘性 → ⑥二创放大，⑧每日复盘贯穿。私人后台仅保存在用户指定私有位置；公开GitHub只存通用方法与虚构样例，不写认证信息、粉丝身份或私人后台数值。
